# v0.6.0 — Governance that lives on one machine is not governance

Three changes, all from one finding: a governed repository moved to a newly
deployed host, and almost nothing came with it. The manifest had never been
committed and the decision store was gitignored on the strength of a remote
nobody configured. The old host has since been decommissioned.

The old host had been reporting `READY_FOR_GOVERNANCE` throughout.

## Governance artifacts are checked for portability (#229)

`engine/manifest.py --validate` now asks whether governance artifacts would
reach another host: the manifest, the acceptance bars, and a file-backed
decision log when one is bound. An artifact a `.gitignore` rule actively
excludes is named as **excluded** rather than merely untracked, because
`git add` alone will not fix that one.

`MANIFEST_UNTRACKED` is advisory and the banner is qualified instead —
`READY_FOR_GOVERNANCE ON THIS HOST ONLY`. It was blocking first, which broke
onboarding: the manifest is legitimately uncommitted between the moment a
proposal is promoted and the moment it is committed, and `--validate` is what
the operator runs in that window. ADR-031 settles the posture for a
configuration gap — report the fact, block nothing.

Portability is asked of the **role, never of a product**. §54 forbids requiring
a named third-party tool and ADR-019 rule 2 says the backend is pluggable, so
each adapter advertises `properties.portable` and the engine warns only when
every bound backend says no.

This repository took its own advice and bound `adapters/decision-history-file`
alongside Dolt. It already shipped, writes tracked JSONL, and supplies
`reversal_condition` and `revision_history` — the two capabilities
`decision-history-github` cannot, and the half a decommissioned host actually
takes away. ADR-019 rule 2 called that pairing *"how portability gets tested
rather than asserted"*; it had never been bound.

`decision_history` is now in `required_roles` for `GOVERNOR_FULL` and
`GOVERNOR_HIGH_ASSURANCE`. No profile required it, though ADR-019 says binding
it is what makes INV-005 and INV-008 enforceable for the first time.

## The signal survey was blind to closed milestones (#231)

GitHub's milestones endpoint defaults to `state=open`. The onboarding survey
did not say `state`, and that count is not advisory — it feeds `unavailable`,
and `ask` **refuses** an unavailable option if chosen. So a repository whose
milestones are all closed was told `milestones : none` and the operator was
refused milestone admission on a repository where it demonstrably works, since
the engine reads `milestone` without consulting its state (#221).

Measured while finding it: 4 open, 6 closed, 10 total. A repository holding
only those 6 would have counted zero.

## Acceptance bars for the four admitted issues that had none (#230)

#159, #197, #200 and #203 were admitted and carried no bar. All four are
unassigned, which was the only reason `conformance/roadmap.py` stayed green —
it fires on milestoned **and** assigned. Each bar names a conformance assertion
rather than holding the only copy of the check.

## This release closes no issues, and files four

Stated plainly because it is the third time. Nothing in these three commits
closed an open issue; the work was found and fixed in one motion, and it
produced **#225, #226, #227, #228**.

That is exactly the pattern #224 is open about: ten of the twelve issues that
shipped in v0.5.0 were never admitted either. Under this repository's declared
admission signal (ADR-018, `signal: milestone`) everything in this release read
`NOT_ADMITTED` while it shipped. Recording it is not excusing it.

## Architecture: the same departure, a second time

The release condition, from RATIFICATION-v0.1.0.md:

> Every architecture decision the runtime depends on is Accepted, and no
> Proposed ADR is silently treated as normative by that release.

Derived by the record's own method — cited by `engine/`, or by an adapter this
repository binds — the runtime-dependent `Proposed` set is:

| ADR | cited by |
|---|---|
| **ADR-031** | `engine/manifest.py`, `engine/status.py` |
| **ADR-033** | `engine/onboard.py` |

**Unchanged from v0.5.0. Not worse, and not better.** Binding a third
decision-history backend added nothing to it.

v0.5.0 shipped as a recorded departure, and that review said what shipping it
again would mean:

> A departure recorded once is an exception; recorded every release, it is the
> condition being repealed by habit.

This is the second consecutive release under the same departure. The set has
not grown, and neither ADR has acquired the evidence it asks for — ADR-031's
conditions need host time this project does not have, and ADR-033's condition 2
would require manufacturing a second branch-varying provider, which the ADR
itself calls writing a provider to pass a test. **#223 is open to settle what
the condition means when a runtime-dependent decision awaits evidence the
project cannot produce.** It is not settled here, and shipping without settling
it is the thing the warning was about.

## Verification

19/19 conformance, hermetic and live. Every new guard proved by mutation in
both directions — the trackedness check especially, since it passes trivially
in the repository that develops it.
